How Do You Move Excel Reporting into a Cloud Data Warehouse?

How to move month-end Excel reporting into Snowflake or BigQuery: finding the sources and rules behind the spreadsheets, the order of work and reconciliation.

By Meet Vaghasia, Founder & Lead Engineer · Published 12 October 2026 · 6 min read

In brief

  • A spreadsheet has become a system of record when its figures cannot be reproduced from the source systems without it. Typed-in adjustments and rules that exist only in formulas are the usual signs.
  • The migration is mostly discovery. Find the sources behind each tab, write the rules down, model them in raw, staging, curated and reporting layers, and reconcile against the last few months of manual figures before any dashboard is repointed.
  • Start with one report, not the whole month-end pack. It proves the design and the reconciliation method on something small enough to correct cheaply.

Few finance or operations teams decide to run reporting in Excel. It happens one workaround at a time, and by the time anyone asks how to migrate Excel reporting to a data warehouse, the spreadsheet is doing a job it was never designed for. This guide covers how to recognise that point, where the sources and rules are hiding, the order of work and what should stay in a spreadsheet.

How do you know month-end spreadsheets have become a system of record?

A spreadsheet has become a system of record when a figure in it cannot be rebuilt from the source systems without the spreadsheet. The test is blunt: if the file were deleted, could anyone reproduce last month's numbers from the systems alone?

The usual signals:

  • Typed-in adjustments. Someone overwrites a cell each month because the source is known to be wrong, and the correction exists nowhere else.
  • Versioned filenames. A file called report_final_v3.xlsx is a change log without the log.
  • Lookups into other spreadsheets. A VLOOKUP into a file on a shared drive is a dependency on an undocumented table.
  • Two numbers for the same thing. The dashboard says one figure, the board pack another, and the spreadsheet is the one people believe.

Each is a reason to treat the spreadsheet as a legacy system with an undocumented data model.

Where are the sources and the rules hiding?

The sources are usually a handful of systems behind the export buttons, and the rules are in the formulas, the pivot filters and the adjustments people apply by hand. More of this discovery happens in conversation than in a database catalogue.

  • Trace each tab backwards. Who pastes into it, from which system, with which filters and date range.
  • Read the formulas as transformation rules. Nested IFs that map codes to categories, SUMIFS with hard-coded dates. Each needs a name, an owner and a test.
  • Collect the rules in people's heads. "We always exclude the intercompany entities." Write them down verbatim, then make them precise.
  • Find the mapping tables hiding in tabs. Cost-centre hierarchies, region lists, owner assignments. These become dimension tables, each with an owner.

The output is a rule register: one row per rule, where it lives today, what it does, who decides it and a worked example from a recent month. Both sides sign it off before anything is built.

What order should the work happen in?

One report first, then source discovery, rules written down, warehouse layers, reconciliation against the last months of manual figures, and only then the dashboard repointed. The order matters because each step produces the acceptance test for the next.

The order of work for moving one spreadsheet report into a warehouse
StepWhat it producesFinished when
1. Choose one reportThe report a decision-maker actually uses, with tabs, inputs and recipients listedEveryone agrees which figures on it must match
2. Source discoveryThe systems, exports, filters and refresh timing behind each tabEvery input cell has a named source
3. Rules written downA rule register with owners and worked examplesNo formula or manual adjustment is unexplained
4. Warehouse layersRaw, staging, curated and reporting layers in Snowflake, BigQuery or RedshiftThe reporting layer reproduces the report's structure
5. ReconciliationAutomated comparison with the last three to six months of manual figuresEvery difference is fixed or documented as deliberate
6. Dashboard repointingPower BI, Tableau or Looker Studio reading the reporting layerThe dashboard matches the signed-off figures, visual by visual

Raw holds the exports as they arrived, so you can prove where a number came from; staging conforms types, keys and dates; curated holds the facts and dimensions, where the rule register becomes code; reporting holds the shapes a BI tool reads. When a reconciliation fails, the layers show which step introduced the difference.

Reconciliation is the step teams are tempted to cut, and the step that decides whether anyone trusts the result. Compare row counts, control totals and every reported figure with the spreadsheet versions, and investigate each difference: some will be defects in the new pipeline, some defects in the spreadsheet found for the first time. Dashboards are repointed last, once the semantic model carries the definitions.

What does a reconciled migration of manual reporting look like in practice?

It looks like a layered warehouse, a written mapping for every object and automated checks against every system that already reports the figures. In a previous engagement at Volvo Cars via Toptal, MV.tech's founder migrated legacy and manual reporting into a Snowflake warehouse with raw, staging, curated and reporting layers, designed fact and dimension models for Power BI with source-to-target mappings, and built validation and reconciliation checks across source systems, Snowflake, Salesforce CRM Analytics and BI reports. Checks of that breadth are what let a manual process be retired on evidence rather than on a date.

What should stay in a spreadsheet?

Analysis, scenarios and anything one person needs for a week. A spreadsheet is the right tool for a question nobody has asked before and the wrong tool for a figure that has to be the same every month.

Keep in Excel: what-if models built on a governed extract, board-pack commentary written next to figures pulled from the reporting layer, and inputs that genuinely originate with a person, such as budget assumptions, provided they are loaded into the warehouse with a timestamp and an owner. Move into the warehouse: any mapping table more than one report depends on, any adjustment applied every month, and any formula behind a figure reported to the board, the auditors or a regulator. The aim is not to ban Excel but to stop a spreadsheet being the only place a rule exists.

What is a sensible first milestone?

One report, reproduced from the warehouse, reconciled against the last three months of manual figures and signed off by the person who used to build it. It gives an estimate for the rest of the pack based on your sources and rules rather than a template.

Pick a report with few sources and a clear owner, agree in advance what "matches" means, run both versions in parallel for at least one close, and insist that handover includes the rule register, source mapping, reconciliation results and refresh schedule. Frequently asked questions

Should we move Excel reporting to Snowflake or to BigQuery?

Either works, and so does Amazon Redshift. Choose by where your data already sits: BigQuery if the sources sit in Google Cloud, Snowflake if you want one platform across clouds. The discovery, the rule register and the reconciliation are the same whichever target you pick.

How long does it take to replace spreadsheets with a data warehouse?

Discovery on the first report typically takes weeks, and the time is driven by the number of sources and undocumented rules rather than by data volume. The rest of the pack is scoped once the first report has been reconciled. We quote after a scoping call.

Will the warehouse figures match the spreadsheet exactly?

Not always, and the differences are the useful part. Some turn out to be defects in the spreadsheet, such as a lookup that silently stopped matching. Each difference is investigated and then either fixed or documented as a deliberate change, with the tolerance agreed before reconciliation starts.
