Migrating a data warehouse to BigQuery: design, steps, costs and checks

How to migrate a data warehouse to BigQuery: dataset and partition design, SQL translation, loading history, cost controls, validation and cutover.

By Meet Vaghasia, Founder & Lead Engineer · Published November 26, 2026 · 6 min read

In brief

  • BigQuery has no servers to size. You design datasets, partitions and clustering instead, and those choices decide both query speed and cost.
  • With on-demand pricing you pay for the data each query scans. An unpartitioned table or a habit of selecting every column can be expensive, so set cost limits before analysts get access.
  • Google’s BigQuery Migration Service assesses the old warehouse and translates SQL in bulk. Translation gives you a first draft. A parallel run is what proves the numbers.

Migrating to BigQuery is less about moving data than about changing how the warehouse is designed and paid for. Teams that copy their old tables across unchanged often get the right numbers and a surprising bill. This guide covers the design decisions to make first, the order of work, the cost controls and the checks before cutover.

What is different about BigQuery?

How do you migrate a data warehouse to BigQuery, step by step?

  1. Assess the current warehouse. Google’s migration assessment reads metadata and query logs from sources such as Teradata and Amazon Redshift and reports what is used. For other sources, build the inventory yourself: tables and sizes, jobs, reports and the queries that run most often.
  2. Design the target. Decide the projects and datasets, commonly separate layers for raw, modeled and reporting data. Choose the dataset location. For each large table, choose a partition column and clustering columns from how it is actually queried.
  3. Set access and cost limits before loading. Grant roles at project or dataset level, add row-level and column-level security where the data requires it, and put query limits in place while the only users are the migration team.
  4. Translate the SQL. The batch SQL translator converts scripts to GoogleSQL in bulk, and the interactive translator handles single queries. Review procedural code, date and time functions, implicit type conversions and anything that depended on case-insensitive comparison, because BigQuery compares strings case-sensitively by default.
  5. Load history. Export tables to Cloud Storage as Parquet or Avro and run load jobs, or use the BigQuery Data Transfer Service to move data from Amazon Redshift or Teradata. Load in date ranges and record row counts and control totals for each range.
  6. Rebuild the pipelines. Point ingestion at BigQuery with your ELT tool, the Data Transfer Service or the Storage Write API for streaming. Rebuild transformations with scheduled queries, Dataform or dbt, and orchestrate them with Cloud Composer or the scheduler you already run.
  7. Run in parallel, then cut over. Load both warehouses from the same sources through a full reporting cycle. Switch each report when its totals match and its owner signs off, keep the old warehouse read-only for an agreed period, then switch it off.

How do you keep BigQuery costs under control?

On-demand queries are billed by the data they scan, so cost control is mostly about scanning less and capping what any one query or person can scan.

BigQuery cost controls to set during a migration
ControlWhat it does
Required partition filterRejects any query on the table that does not filter on the partition column
Maximum bytes billedStops a query before it runs if it would scan more than the limit
Custom quotasCaps the data a user or a project can scan in a day
Dry runReports how much data a query would scan without running it
ClusteringReduces the data scanned when queries filter on the clustered columns
Capacity pricingReplaces per-query billing with reserved slots for steady, heavy workloads

Two habits matter as much as the settings. Select only the columns a query needs, because BigQuery stores data by column and SELECT * reads all of them. Point dashboards at small reporting tables or views built for them, not at raw fact tables.

How do you check the migrated data?

Use the same three levels as any warehouse migration: row counts by partition, control totals by period, and the figures on the reports people use, agreed with the old report for closed periods. Google’s open-source Data Validation Tool can run count and aggregate comparisons between the source and BigQuery. Our guide to checking a reporting migration describes the sign-off process.

When totals differ, these are the usual causes:

  • Time zones. A BigQuery TIMESTAMP is a point in time in UTC, and a DATETIME has no time zone. Daily totals shift if a source column stored local time.
  • Numeric types. Use NUMERIC for money, not FLOAT64. Floating-point totals drift by small amounts that grow with volume.
  • Text comparison. Joins and filters that matched regardless of case, or ignored trailing spaces, in the old warehouse may not match in BigQuery.
  • Duplicates. Keys are not enforced, so a rerun load can insert the same rows twice unless the pipeline prevents it.

Common mistakes in a BigQuery migration

  • Copying the old design unchanged. Large tables without partitions make every query scan the full history.
  • Opening access before limits are set. One exploratory query on a large table can cost more than a month of planned usage.
  • Creating datasets in the wrong location. If data must stay in a particular country or region, that has to be decided before the first load.
  • Trusting translated SQL without tests. Translation preserves syntax more reliably than meaning.
  • Skipping the parallel run. It is the only stage that shows whether the reports still agree.

Frequently asked questions

How long does it take to migrate a data warehouse to BigQuery?

The schedule follows the number of pipelines and reports, not the amount of data. A first subject area usually takes weeks. A whole warehouse takes months, and the parallel run sets the minimum because it has to cover a full reporting cycle.

Is BigQuery cheaper than our current warehouse?

It depends on how the data is queried. BigQuery costs little when idle because there is no cluster to keep running. It can cost more than expected when large tables are scanned often without partition filters. Estimate with dry runs of your real queries before you commit.

Should we use on-demand or capacity pricing?

Start on-demand while volumes are small or hard to predict, with quotas in place. Consider capacity pricing once monthly query spend is steady and high enough that reserved slots would cost less.

Can Power BI or Tableau report from BigQuery?

Yes. Both have BigQuery connectors. Connect them to reporting tables or views, and use imported or aggregated data for dashboards that refresh often, so that each view does not start a large scan.
